0. CLARIFICATION PRODUIT (À NE PAS CONFONDRE — VALIDÉ PAR LE PORTEUR)
--------------------------------------------------------------------------------

Objectif final : 3 TYPES d’utilisateur — chacun avec SES routes, SON UI, SES fonctionnalités.
  • Pas d’« autorité » qui se retrouve sur l’UI opérateur ou modérateur parce qu’elle a besoin
    d’une fonctionnalité : les capacités utiles d’opérateur / modérateur sont RAPATRIÉES dans le
    PARCOURS et l’INTERFACE « autorité » (police / gendarmerie), pas en réutilisant les anciens
    écrans / routes operator ou moderator comme raccourci.
  • Pas de mélange confus entre « admin système » et « admin org » au niveau UX : deux espaces
    distincts ; seules les fonctionnalités importantes de l’ex-admin org qui relèvent de la
    GESTION DU SYSTÈME sont du ressort de l’admin système (pas « tout l’ancien admin org »).

Ce qui est fusionné vers AUTORITÉ (sens métier / produit), et ce qui ne l’est PAS :
  • OUI — rapatrier les fonctionnalités de l’OPÉRATEUR et du MODÉRATEUR qui n’existent pas déjà
    chez les autorités, dans le cadre UI + routes « autorité » (police / gendarmerie).
  • NON — les fonctionnalités ONG ne sont PAS données à l’autorité (police / gendarmerie). L’ONG
    n’est pas absorbée dans le parcours autorité.
  • Portail dédié `/ngo` : **non requis** (décommissionné côté app — redirection vers `/authority/dashboard`).
    Les écrans ONG en code restent **réutilisables** sous `/admin/*` (basePath admin) si une org en a besoin.

Rôles en base (3) vs silos UX (3) :
  • En base après migration : citoyen | autorite | admin_systeme.
  • En UX : trois silos — Citoyen | Autorité (police/gendarmerie + ce qu’on rapatrie d’op./mod.) |
    Admin système (+ portail org /admin pour admin_systeme avec org, distinct de /super-admin).

1. VISION PRODUIT (RAPPEL — CORRIGÉ)
--------------------------------------------------------------------------------

Grand public
  • Compte non obligatoire au début ; incitation à créer un compte après interactions.
  • Option retenue (étape A) : comptes invités / anonymes + upgrade vers compte complet.
  • Signalements « optimistes » : feedback immédiat « bien reçu » ; traitement / tri côté autorités.

Réduction à 3 types / 3 rôles en base
  • citoyen — grand public ; « vérifié » = statut (attribut).
  • autorite — police / gendarmerie ; enrichi des manques fonctionnels opérateur / modérateur
    UNIQUEMENT, intégrés dans l’UI autorité (pas ONG).
  • admin_systeme — gestion plateforme ; création des comptes autorité : admin système seul.

Après migration 20260423 : admin_systeme unique en base pour le « côté admin ».
  • /admin : admin_systeme + id_organisation (gestion liée à une organisation).
  • /super-admin : admin_systeme sans org (gestion globale système).

2. ACTIVER LES COMPTES ANONYMES (ÉTAPE A — CE QUI MANQUAIT CÔTÉ « COMMENT »)
--------------------------------------------------------------------------------

La décision A (invité/anonyme) était validée ; le « j’attends » venait du fait de ne pas savoir
comment activer sur Supabase. Procédure courte :

  1) Supabase Dashboard → Authentication → Providers (ou Sign in / Providers selon UI).
  2) Activer « Anonymous sign-ins » (ou équivalent).
  3) Côté app : utiliser le flux Supabase « sign in anonymously » puis « link identity » /
     upgrade quand l’utilisateur crée un vrai compte (doc Supabase : Anonymous Sign-Ins).

Tant que ce n’est pas fait : l’étape A reste « partielle » uniquement sur cette livraison technique,
pas sur le choix produit.
